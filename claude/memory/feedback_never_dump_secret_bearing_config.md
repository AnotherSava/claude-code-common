---
name: Never dump a secret-bearing config section
description: To check a setting in a config file, print only the named keys or masked values — a whole section can carry a credential into the transcript
metadata:
  type: feedback
---

When reading a config file to check a setting, print only the keys the question needs, and mask any value that could be a credential. Never print a whole section or the whole file.

**Why:** on 2026-09-27 a quick check of two flags in a desktop app's `config.json` printed its `notifications` block wholesale, and that block held a Telegram bot token in plaintext. Once a value is in the transcript it has left the machine, so the only remedy was rotating it — which took a BotFather revoke, a Doppler update, a redeploy and a sweep for other copies, and ended in switching bots. Nothing flagged the print: the file was not named like a secrets file, and the safety classifier that blocks an explicit `doppler secrets get` let a `json.load` + `print` straight through.

**How to apply:** select the keys by name (`c['high_alert']`, not `c['notifications']`), or print structure only (key names, value types, lengths, a masked prefix such as `sed -E 's/("[^"]*token[^"]*": *")([^"]{6})[^"]*"/\1\2…"/'`). Treat any config that feeds a notifier, a sync peer, an API client or a deploy as secret-bearing until shown otherwise. Git's own config counts: in a transcrypt repo `git config --list` prints `transcrypt.password`, and on 2026-09-28 an audit of stray local settings did exactly that, within the hour of this rule being committed. Ask for the keys in question with `git config --get <key>`. The git shapes are now refused before they run by `hooks/secret-print-guard.py`, masked reads of `.git/config` included, so for git's own config the masked-prefix form above does not apply: use `--get` or `--list --name-only`. **A key whose *value* is the secret has no read form at all** — `--get transcrypt.password` is refused exactly as `--list` is, and capturing it into a variable does not help, because the guard cannot see what happens after. Confirm presence with `--name-only`, and derive anything further: to ask whether a clone's configured key is the one its blobs are under, run that repo's own clean filter over an unchanged `*.secret.*` file **from inside that repo** and compare `git hash-object --stdin` against `git rev-parse :<path>` — a match proves it, and reads no key. Run it from another checkout and transcrypt resolves *that* repo's key instead, silently. It cannot say *which* key that is, so it never answers "has this repo been rotated yet"; for that, decrypt the origin blob with Doppler's value and assert openssl's exit status, per `learnings/transcrypt-verify-before-commit.md`. What the guard cannot see is a script that loads a config and prints part of it, which is this memory's to catch. When a value genuinely has to be used, pipe it straight into its consumer as `/doppler` describes, and report a derived fact (a length, a `getMe` username, a digest) rather than the value. See [[feedback_doppler_secrets]] and [[feedback_rotate_dont_abandon]].
