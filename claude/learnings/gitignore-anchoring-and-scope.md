# Gitignore anchoring and scope (where an ignore rule should live)

## Anchoring: which patterns are pinned to the base directory

Git decides whether a pattern is anchored to its *base directory* by where the slashes are:

- **Leading slash** (`/scripts/`) → anchored to the base; matches only at that level.
- **Mid-string slash** (`scripts/deploy.sh`) → **also anchored**. A slash anywhere except the trailing position anchors the pattern, so `scripts/deploy.sh` and `/scripts/deploy.sh` are equivalent — both match only `<base>/scripts/deploy.sh`, never a nested `sub/scripts/deploy.sh`.
- **No slash, or a trailing slash only** (`scripts/`, `*.log`) → *floats*: matches at any depth. `scripts/` ignores a `scripts/` dir anywhere in the tree, including `web/scripts/`.

The **base directory** is:
- the directory containing the `.gitignore`, for a per-directory ignore file;
- the **repository root**, for the global excludes file (`core.excludesfile`) and `.git/info/exclude`.

So a leading or mid-string slash in the *global* excludes anchors to each repo's root.

## The whole-dir-in-global trap

Putting a floating whole-dir pattern like `scripts/` in the **global** excludes ignores the root `scripts/` directory of *every* repo you touch — including the many that commit a real `scripts/` (build/util scripts). Verified with a throwaway repo + `git check-ignore -v` against a global `core.excludesfile`:

| global pattern | `scripts/deploy.sh` | `scripts/build.mjs` (committed) | `sub/scripts/deploy.sh` |
|---|---|---|---|
| `/scripts/deploy.sh` | ignored | safe | safe |
| `scripts/deploy.sh`  | ignored | safe | safe (mid-slash auto-anchors) |
| `/scripts/` (whole dir) | ignored | **HIDDEN** | safe |

Rule of thumb: **never put a floating or whole-dir pattern in the global excludes** — only narrow, root-anchored *file* patterns (or genuinely user-global dirs like `.idea/`, `.ralphex/`).

## Where an ignore rule should live

- **Global excludes** — resolve the file with `git config --global core.excludesfile` (on this setup `~/.gitignore`, symlinked from the dotfiles repo; there is no `~/.gitignore_global`). Home for user-/tool-specific artifacts no contributor shares: IDE folders, OS caches, and **per-machine wrappers generated by personal Claude Code skills**. The deploy/build skills' `scripts/deploy.sh` and `scripts/build.sh`, plus `config/deploy.env`, live here as narrow file patterns — one rule covers every repo, and nothing leaks into a shared/public project's committed `.gitignore`. (Consequence: `config/deploy.env` is machine-local and never committed, even for dev-server projects where the deploy skill's text calls it "safe to commit".)
- **Project `.gitignore`** — files every contributor should ignore: build outputs, `.env`, `node_modules/`, and project-structure-specific artifacts whose path depends on the layout (e.g. a dev server's `<DEV_DIR>/dev-server*.log`). Anchor with a leading slash (`/scripts/`) unless matching at any depth is intended.
- **`.git/info/exclude`** — per-repo, uncommitted, local-only. The purist spot for "ignore this here, just for me" without leaking into the committed file; downside: invisible and lost on re-clone.

## Per-project → global migration checklist

When moving a wrapper ignore from per-project entries to one global rule:

1. Add the narrow file pattern(s) to the global excludes (`scripts/deploy.sh`, `scripts/build.sh`).
2. Before deleting a project's whole-dir `scripts/` entry, confirm `scripts/` holds **only** the wrapper — a whole-dir ignore can be silently hiding real sibling scripts. Check with `git status --ignored --porcelain -- scripts/` and `git ls-files -- scripts/`. If a real script is hidden (e.g. a `save-icons.py` next to a tracked `package.ts`), removing the entry would expose it — that is a per-file decision to surface, not a blind removal.
3. After removing, verify the wrapper is still ignored (now via global): `git check-ignore -v scripts/deploy.sh` should point at the global file, and `git status` should show nothing newly exposed.

## `git check-ignore` exit 0 means "a pattern matched", NOT "the file is ignored"

The exit status answers *did any pattern apply*, and a **negation** applies just as much as an exclusion.
So a re-included file — one covered by a `!` rule — also exits 0, and a script that reads the status as
"ignored" gets the answer backwards on exactly the files a negation exists to protect.

Measured with a throwaway repo, a global `core.excludesFile` containing `config/publish.env`, and a
repo-level `.gitignore` containing `!config/publish.env`:

```
$ git check-ignore -v config/publish.env
.gitignore:1:!config/publish.env	config/publish.env      # note the leading !
$ echo $?
0                                                        # matched — and NOT ignored
$ git add config/publish.env                             # succeeds without -f
$ git status --short --untracked-files=all
?? config/publish.env                                    # visible
```

**Read the `-v` output, not the exit code.** A leading `!` on the reported pattern means the file is
*not* ignored. Without `-v` there is nothing in the result that distinguishes the two outcomes.

The behavioural checks are unambiguous where the exit code is not:

```
git check-ignore -v <path>                     # inspect the pattern; ! prefix = not ignored
git add --dry-run <path>                       # errors on a genuinely ignored path
git status --short --untracked-files=all       # an ignored path never appears
```

This bit twice in one session. First a test concluded "the negation does not work" from exit 0, while
`git add` in the same script was succeeding — two contradictory signals, and the exit code was the wrong
one to trust. Second, a repo-level negation of a global rule is a supported and useful arrangement (it is
how one repo opts a path back in without weakening the default for every other repo), so getting this
backwards means rejecting the right design for a measurement error.

Also worth auditing: any instruction of the form "`git check-ignore` must exit 0" written near a `!`
pattern is probably asserting the opposite of what it intends.
