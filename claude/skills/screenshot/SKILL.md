# Screenshot

Owns everything from the moment a picture is going to change until the user has ruled on it: taking it through a recorded script, framing it, filing it with an undo path, and showing it on a contact sheet. Deciding *whether* a frame is stale, and whether its `policy` permits a replacement, is `screenshot-relevance`'s; this skill starts where that one stops, or where the user asks for a picture directly.

## Context
- Repo root: !`git rev-parse --show-toplevel 2>/dev/null || pwd`
- Screenshot manifest: !`R=$(git rev-parse --show-toplevel 2>/dev/null || pwd) && cat "$R/docs/screenshots/screenshots.json" 2>/dev/null || echo MISSING`
- DocShot installed (macOS): !`test -d ~/Applications/DocShot.app && echo PRESENT || echo MISSING`

Bare `scripts/` and `references/` paths below are this skill's own, under `~/.claude/skills/screenshot/`, and a project calls them there rather than copying them in. Every other path is relative to **Repo root**.

## Process

1. **Find the frame's entry and read the manifest reference.** Locate the screenshot in **Screenshot manifest** and read `~/.claude/skills/screenshot/references/screenshot-manifest.md` before writing to it — the schema, `capture.command` and `capture.steps`, and the upkeep rules. When the manifest is `MISSING`, the frame gets an entry as part of filing it, with no `policy` key: that field is the user's to give.

   **A direct request is the permission.** When the user asks for a frame and names the state, capture it whatever its `policy` says; a `never` entry stops `screenshot-relevance` from *offering* a replacement, not the user from asking for one. When the request does not name the state and the UI now has several, ask which one before going further.

2. **Ask immediately before taking the machine.** A capture that raises a window, moves the pointer, synthesizes input, or launches or relaunches the app takes the machine, and needs the user's yes right before it runs — never folded into the request that started the work. Say which app and windows it touches and roughly how long it takes. A capture with no window of its own — a headless browser rendering a fixture, a DocShot shot of a window the user already has on screen with `open -g` — needs no ask.

   Read the capture script before asking, so the question names what it actually drives. A script that needs the pointer clear of the subject parks it itself, inset from every screen corner, and restores it in a `finally`; it does not refuse and hand the move to the user (`~/.claude/memory/feedback_capture_takes_the_pointer.md`). Run as a fork, as inside `screenshot-relevance`, this skill cannot ask: report such a capture as pending with its command and stop.

   On macOS, check **DocShot installed (macOS)** first. When it is `MISSING`, build it with `bash ~/.claude/skills/screenshot/scripts/build-docshot.sh` and ask the user to grant it Screen Recording before the run; the Screen Recording switch reading on for the terminal is not evidence the terminal holds the grant, which is why the capture goes through DocShot.

3. **Keep the outgoing file before anything overwrites it.** Copy it to `tmp/screenshot-originals-<date>/` — the reversibility rule under step 6 says why and for how long.

4. **Capture by script.**
   - **Every capture runs a script, including the first one.** Wherever a capture is permitted — `confirm` after approval, `auto`, a named-state request, or an approved gap — run the entry's `capture.command`: a recorded script reruns identically, lands in the diff, and does not depend on the machine's window size, theme or which apps are open. When no command exists yet, **write the script rather than driving the app ad hoc**: turn `capture.steps` into `docs/screenshots/capture/<id>.sh` (or `<id>.ps1`, run with `pwsh -File`, for a Windows capture), run it, iterate on the script until the frame is right, then record it in `capture.command`. That directory is the only capture surface this skill drives directly, which is deliberate — it makes the second capture free and the diff reviewable, and it stops a one-off sequence of clicks from becoming the only record of how a published image was made. The script is what reruns; the staging and the shutter below are what it calls. A capture script builds against the current working tree, never an installed release, or the shot documents a build nobody has.
     - **The machinery lives in this skill; only the staging lives in the project.** Anything a second project would want unchanged — taking the picture, driving a browser, trimming a halo, stroking an edge, converting a colour profile — belongs in `~/.claude/skills/screenshot/scripts/` and is *called* from the project, so a fix reaches every project at once and two copies cannot drift. What belongs in `docs/screenshots/capture/<id>.sh` is what only this project knows: which window or route, which state to stage, which region to crop, which sessions may appear in frame, which week the chart should show. Two smells mark the boundary moving: a capture script that has grown image-processing code has almost always grown a second copy of something shared, and a script in this skill that knows an app's window title has taken on something it cannot know for the next project. Copying a helper into a project to avoid depending on a path under `~/.claude` is the wrong trade — that path is the same on every machine these dotfiles are installed on, which is exactly the condition under which the capture runs at all.
   - **If the capture runs off fixture data, build the fixture the frame needs.** A script that renders from whatever fixture was already lying around produces a correct picture of the wrong moment — a history with no compound action, a deck with nothing identified — and quietly stops illustrating the sentence beside it. That is a fixture problem, not a reason to accept a thinner shot or to go back to shooting by hand. Find the real session the original came from (its distinctive content is the search key — a card name or a label visible in the old frame will often identify it outright), commit the smallest artifact that reproduces it, and add whatever flag selects the moment. Prefer a processed intermediate to raw capture data when the renderer accepts one — an order of magnitude smaller, and the parser that produces it has its own tests. Keep this data out of the product: a fixture beside the capture scripts is documentation support, and it must never become a seed-data hook in the shipped code.
   - **Match the device pixel ratio of the shots you are not replacing.** A hand-taken screenshot carries the DPR of the display it came from — commonly 1.5 or 2 on a scaled monitor — while a headless capture defaults to 1. The replacement is then correct and renders about a third smaller, which no text check can see and which shows up as two apparent zoom levels on one page, since the un-replaced frames beside it are still at the old ratio. Measure it rather than guessing: a repeating feature in the old shot (a card, a row, a cell) against the same feature rendered at 1 gives the ratio directly, and the numbers land on a clean value. Match the framing width the same way — the old shot's pixel width, less 2 × the ring width when `hairline.py` framed it outward, divided by that ratio is the CSS width it was taken at, and a wider viewport silently shrinks everything laid out to fill it.
   - **A re-shoot keeps the subject of the shot it replaces.** Same week on a chart, same project and same scroll position in a log or a conversation, same record in a list — change only the thing the re-shoot exists to change. Three reasons, and the first is the one that bites: the prose around a figure, its alt text and its caption were written against *that* frame, so a new subject silently re-points every sentence that refers to it, and the check above cannot catch it because the words are all still true of something. Second, a paired figure — one variant per platform — is read as two pictures of one thing, so two subjects turn a comparison into a puzzle. Third, an image diff is unreviewable: holding everything else still is the only way the intended change is visible at all.
     Record the anchor in the manifest entry's `capture.steps` — which session, which week, which point in the history — in the same breath as capturing, because it is knowable now and expensive to recover later, and the next re-shoot is the run that needs it. Where the script can take it as a parameter, give it a default rather than leaving it to whatever is on screen.
     **When the old subject genuinely cannot be used, say which one it was and what replaced it** rather than quietly picking a new one. Private content in the frame, a session that no longer exists, a chart week that has aged out of the data — all real, and all reasons the user should hear once, not discover later from a figure that stopped matching its paragraph.
   - **Writing that script: staging, then the picture.** Two separate problems, and they are worth keeping apart: *staging* the thing (getting the right window open, showing the right content) and *taking the picture*.
     **Staging — climb down from the top, never start at the bottom.** In order: (1) the app's own interface — a URL scheme, CLI, or local HTTP route — which needs no OS permission, says what it means, and does not break when the UI moves; (2) App Intents / `shortcuts`; (3) Apple Events against the app's scripting dictionary, whose Automation grant is scoped *per source→target pair*; (4) the Accessibility API, semantic but a system-wide grant; (5) synthesized clicks at coordinates. Rung 5 needs the same broad grant as 4 while being strictly more fragile, and a helper that injects input is a general "control this machine" capability — expect it to be refused, and do not treat that as an obstacle to route around. **For an app the project owns, the answer is usually to give it rung 1 rather than to puppet its UI** — that is a legitimate control surface, and distinct from the in-product capture hooks the rules below forbid: it drives the product through the same door real use does. A fixture replayed through that door stages the content, and the rules below say how.
     **Taking the picture** needs Screen Recording on macOS, and where that grant goes matters. Not to the agent's own binary: it is version-named, so the grant goes stale on every update, and it would hand whole-display access to every session forever. A small purpose-built helper at a fixed path with a stable signature is granted once and scoped to the one job — `~/.claude/skills/screenshot/scripts/` holds `docshot.swift` (capture) and `build-docshot.sh`, which installs it as `DocShot.app` and refuses to clobber an existing install, since rebuilding resets the grant. Two traps that cost real time: TCC attributes the request to the **responsible process**, so the helper must be launched through LaunchServices (`open -a … --args`) or the grant is ignored and it must therefore return results in a file rather than on stdout; and a denial is silent — window ids, owners and bounds still populate while every *title* comes back empty, so probe for that (`--check`) rather than discovering it as a black PNG. **On Windows no grant is involved, and the shared machinery is PowerShell:** `window-shot.ps1` is the shutter (`-Method PrintWindow`, `Screen`, or `Alpha`, the two-backdrop solve below; `-Popup` for a menu), and `windows-capture.ps1` is what a project's `<id>.ps1` dot-sources to reach it — `Invoke-WindowShot`, `Add-WindowFrame`, `Invoke-WithPointerAt`, `Get-PrimaryWorkArea` and `Find-ProcessWindows`. A project whose Windows captures dot-source this `windows-capture.ps1` runs `~/.claude/skills/screenshot/scripts/check-capture-scripts.ps1` from its commit gate, from the repo root — captures built on a library of their own give it nothing to check, and it fails on them: it resolves every function, parameter and type the captures use from this library, so renaming one here fails that project's commit instead of its next capture, which would otherwise break after the pointer has moved.
     Then the honesty rules that make the result worth committing:
     - **A screenshot of an empty app is worse than no screenshot.** Most UI worth documenting only looks like itself with real content in it — a session list with sessions, a chart with history, an inbox with mail. When real use does not supply that content, replay a fixture (next rule) rather than shipping a picture of an empty shell; hand the capture back to the user only when neither can reach the state.
     - **Stage the state through the product's own input, never inside it.** Two sources are legitimate: real use, and a **fixture replayed through an input the product already takes** — synthetic hook events posted to its event API, a recorded file its importer reads, a URL its router accepts — kept beside the capture scripts. Prefer the fixture whenever the frame needs a particular spread of states: it reproduces the same frame on every run, keeps private project names and real prompt text out of the picture because every string in it was chosen for the shot, and needs nobody's live sessions arranged by hand. Name its rows after the user's own public projects, not invented sample names (the user's call, 2026-09-26); only the prompt text and labels are written for the shot. Measured 2026-09-25: staging real sessions for one frame took three failed launches and still produced badges nobody wanted in the picture. Either way the pixels must be the real product rendering a state it can reach from that input:
       - never a demo mode, seed data or fixture path inside the product — the demo-mode rule under **Out of scope**;
       - never a hand-edited or composited frame;
       - never a fixture that makes the product show what its code cannot produce from real input, such as a label no event maps to.

       Undo whatever the replay leaves in the product's own stores — a history file, a cache, a session index — before handing over, so the fixture does not outlive the capture.
     - **Crop to the subject.** A whole-desktop grab of a small widget documents the wallpaper. Capture the window, not the screen. **And take all of the subject, corners included.** When what you are capturing has rounded corners — a dialog, an IDE's island panel, a card — the capture takes its full bounds so its own arcs are in frame, and the background outside them is removed by the two-backdrop solve or the known-shape mask (*Capture the background out* and *A known shape needs only one capture* below), never cropped away. A rectangle inset past the arcs discards the real corners and keeps faint remnants of them at the edges, and no later step gets the shape back: rounding the inset crop with `hairline.py --radius` imitates corners the capture threw away. In-process, that means painting the component that draws the rounded shape — the island, not the editor inside it — and on screen, capturing to the shape's bounds rather than inside them. **Where the cut goes is read off the pixels:** capture with some background beyond the shape on every side, then crop with `scripts/outline.py`, which compares each row and column with its own outermost pixel — a window's backdrop can be a tinted gradient — and cuts on the first pixel that differs, so the line sits just outside the shape and its antialiased edge stays in. A cut placed on the border line, or on bounds taken from the layout, trims that edge off the flats and bites into the arcs.
     - **A cut through content keeps every glyph on one side of it.** A side that is not the subject's own outline — a crop out of a larger view — passes through whatever lies there, and the sliver it keeps of a letter or an icon reads as a stray contrast spot against the frame rather than as the edge of a crop. Clean every such side with `scripts/outline.py --sides <outline sides, or none> --clean SIDES --reach N`. `--sides` names only the sides that are the subject's own outline, which are cut on the first pixel unlike the edge; every other side stays where it is, and a crop with no outline of its own takes `--sides none`. Left out, it defaults to every side `--clean` does not name, and a side named by both is refused. `--clean` moves the cut inward to the nearest line that cuts no glyph in two (the fewest, when none within reach is clear) and leaves a cut that is already clean where it is. A glyph that only touches the cut is whole and does not move it. It judges a cut by the line it drops, so run it on a capture that reaches past every side it cleans; at the image's own edge it has to move at least one line. Keep `--reach` inside the gap between the cut and anything that must stay whole, since it counts glyphs cut in two, not a border the new cut would run along.
     - **Frame with an even margin, and let the pixels decide it.** A subject that stretches to its container, a page shorter than its own bottom padding, or a grid whose widest row stops short each leave a band of background on one side and none on the other — and choosing a viewport width only frames a subject that happens to fill it. Trim to the pixels actually drawn and pad back out to a uniform margin, so the frame is even whatever the subject did. Pad outward rather than clipping a wider region: on a stacked layout the neighbour sits a few pixels away, so a generous clip frames the subject with someone else's content. Do not do this to a shot over a textured or photographic background — the trim keys off a flat background colour, finds "content" everywhere, and pads a solid-colour border around the outside; a hand-cropped shot of a real page is usually already tight, so leave it.
     - **Capture the background out, don't crop it out.** Anything that isn't a plain rectangle — rounded window corners, a drop shadow, a translucent overlay — has boundary pixels that are a *blend* of the subject and whatever was behind it, so no crop separates them: trimming either leaves a grey fringe or eats content, and for a genuinely translucent window there is nothing to trim at all. Photograph the subject twice over known backdrops instead and solve `O = C·a + B·(1−a)` per pixel for its real colour and coverage, writing a PNG with an alpha channel. The shot then composites correctly on a light page or a dark one, which a baked-in background never does. Treat a stray dark or light fringe at a corner as this problem, not as a crop that needs another pixel or two — a rectangular trim is the *diagnosis* (corners that stay the backdrop's colour prove the subject is round), never the remedy.
       **Do not re-derive this.** On Windows it is already implemented as `window-shot.ps1 -Method Alpha`. `~/.claude/learnings/windows-window-capture.md` carries the solved form (`a = 1 − (O_w − O_k)/255`, `C = O_k / a`), how to place the backdrop, and two things the formula alone will not tell you: **the recovered colour is also the diagnosis** — a fringe coming back as the subject's own colour at rising alpha is background and the alpha removes it, while one coming back *dark at ~50% coverage* is the window's own chrome, which no keying will touch and which must instead be inset past — and that verifying with a threshold tuned to the previous defect sails straight past the next one. **A backdrop need not be a window behind a window**: for anything rendered in a page — a web app, a themeable UI — the two known backdrops are two values of its own background, which is usually one line of CSS and easier than the desktop case the learning was written for.
     - **A known shape needs only one capture.** The two-backdrop solve exists because both the colour and the coverage are unknown at a boundary pixel. When the subject is a shape you can describe — a rounded rectangle, a panel, a card — its **geometry supplies the coverage**, and a single capture is enough: build the mask analytically, supersampled, and apply it. Two details decide whether it looks right. **Inset one pixel**: a mask alone leaves a fringe, because the pixels it half-covers really are half backdrop, and dropping that ring takes the fringe with it at the cost of a corner a pixel tighter — invisible at viewing size. **Do not un-blend an inset edge**: with an inset the boundary sits inside the subject, so a partial pixel is pure subject being antialiased, and subtracting a backdrop that is not in it over-brightens toward white (seen as a 7%-alpha white fringe that passed every numeric check). Un-blending is correct only at zero inset. Masking by shape also sidesteps a backdrop too close to the subject to colour-key — in one case 28 levels of blue apart. Two consequences: the border that follows must trace the **shape**, since a keyed image has no rectangular edge for a canvas-wide box to sit on; and estimate the subject's own luminance from a **median over a grid**, because a single sample lands on text as readily as on fill and will pick a dark outline for a dark panel.
     - **Give a screenshot an edge when its own capture has none.** This applies to every frame the skill files, not only to ones captured by script — the `screenshot-relevance` skill's *Every published frame carries an edge* runs the same check on inherited and user-supplied frames too. A shot whose border colour matches the page it lands on has no visible boundary — a dark app on a dark page, a light app on a light one — so the reader cannot see where the picture stops, and **you do not get to choose the page**: a docs site pinned to a light scheme still has its README rendered by github.com in whichever theme the reader uses, so "the site is light, so a dark frame shows its edge" is never a reason to skip. macOS draws a *decorated* window a light hairline and transparent rounded corners for free, which is why a shot of one already reads correctly; an **undecorated** window has neither, a **dark-themed** decorated window gets no light stroke either, and a region crop never does. **The edge belongs in the image, not the stylesheet** — `~/.claude/skills/github-pages/SKILL.md` gives the reasoning, of which the decisive part is that no CSS reaches `README.md`, which github.com renders in dark mode. Bake it with `scripts/hairline.py`, called from the project's capture script the way the capture helper beside it already is — a plain CLI precisely so the PowerShell half of a cross-platform project can shell out to the same one. This is framing, not retouching, and it moves nothing: on a fully opaque frame the edge goes in a new margin outside and every captured pixel survives, bar the corners `--radius` clips when asked to round them; on a shaped frame it recolours only the outermost band inside the silhouette, where the OS would have drawn its own edge.
       - **Check all four sides, at any alpha, before adding one.** Two probes that look sufficient are not. Sampling only the top edge called a dark-themed window bordered when three of its four sides were bare — its top row was the title bar's own highlight. Sampling only pixels above `alpha 200` cannot see a translucent border at all, and reported plainly bordered Windows frames as bare; theirs measures `(101, 101, 101)` at `alpha 119`. A window either has a frame all the way round or it has none, so at every position along the middle half of each side walk in as far as the midpoint, compare the outermost pixel above the antialiased fringe — alpha 64 or more, low enough to include Windows' band, high enough to step past a keyed frame's alpha-18 fringe — against one a few pixels further in, and count a side bordered only when most of its positions contrast — a border differs from the content behind it nearly everywhere, text only where a glyph falls, and one midpoint probe per side called a bare crop of editor text bordered. Require three sides of four. `has_own_edge` in that script is the implementation.
       - **Derive a shaped frame's ring from its own alpha; never draw a shape over it.** The one drawn shape is `hairline.py --radius` on a fully opaque frame whose subject's corners really are circular arcs (next bullet). macOS does not round a window with a circular arc — its corners are continuous, so no radius makes `CGPath(roundedRect:)` or Pillow's `rounded_rectangle` sit on the curve, and both were tried. Worse, compositing a drawn stroke takes the output alpha from the source, so wherever the arc falls outside the real corner it paints new opaque pixels and quietly *enlarges the window*. Eroding the alpha and subtracting cannot do either, because the ring is a subset of the shape by construction. Erode with a **disk**, not a square: a square kernel — all `ImageFilter.MinFilter` offers — erodes `w` along the axes and `w·√2` diagonally, which is a border 41% thicker everywhere the edge curves, and a ratio of exactly √2 between corner and flat is that bug's fingerprint.
       - **A square frame gets its edge outside, never inside.** The inward ring is right for a shaped frame, whose edge is antialiased coverage. On a frame with square corners — every region crop, and any capture with no transparent pixel — a ring inside the silhouette paints over the outermost pixels of content, which on a crop are the pixels right at its cut sides. `hairline.py` grows a fully opaque frame's canvas by the ring width on every side instead, so every captured pixel survives, bar the corners `--radius` clips, and the file comes out 2 × width larger each way. Rounded corners come from the subject's own arcs, which a whole capture keeps (per *Crop to the subject*). An opaque whole capture still carries backdrop outside those arcs, so once `outline.py` has cut it to its outline, `hairline.py --radius N` at that outline's radius is the known-shape mask that removes it; without the flag the frame comes out square with backdrop in its corners. The same flag is also the fallback for a capture cropped inside its corners that cannot be taken again, where it imitates corners the crop threw away. Use it either way only when the corners are circular arcs, such as an IntelliJ Islands panel: the content is clipped to radius N at its own extent and the ring follows it outside, with `--cut` keeping a crop's cut corners square.
       - **Decide square or rounded from the subject, not from the alpha.** A capture of a whole window or dialog is rounded — 8 DIP on Windows 11 — even when it arrives as an opaque rectangle: `PrintWindow` returns the window's own surface without DWM's rounding, opaque at all four corners (measured in `~/.claude/learnings/windows-window-capture.md`), and a crop taken just inside the border keeps only faint arcs of it at the corners. **Those arcs are the evidence, so look for them.** An opaque crop that shows no trace of an arc at any corner — one cut well inside the dialog, through a scrollbar or a list — is a region crop, whatever it shows: it gets a square frame from `hairline.py`, or a new capture of the whole window, never `-Grow` and rounded corners, which would imitate corners the crop never had. `hairline.py` sees an opaque rectangle and squares it off, so a window capture keeps its shape through `winframe.py` instead (`Add-WindowFrame` from a capture script). A new capture takes the window to its own bounds, which `window-shot.ps1` does by cropping to DWM's extended frame. When a capture already sits just inside the window's border — faint arcs at its corners — and cannot be taken again, pass `-Grow` (`--grow` to `winframe.py`): it grows the canvas by the border thickness first — 2 px at 144 DPI — so the content is clipped to the capture's own extent and the frame lands in the new margin, outside it. The ring `Add-WindowFrame` passes is `#BDBDBD` opaque, the colour `hairline.py` strokes, so the rounded frames and the square ones read as one set.
       - **A crop of a translucent-bordered window needs its border replaced, not tinted.** Windows draws a window's frame as a 2px band that captures at `alpha ~120-150`, so a crop of one keeps a real border on its uncut sides and has none on the cut ones — and writing colour alone can never make the two agree, because the kept sides stay translucent and take their tone from whatever is behind the page. Measured on a cropped tab strip: the native two read `~162` on a white page and fell to `53` against a `46` background on a dark one, while the stroked two read `189` on both — reported as a *darker* border, which it is, on the half of the picture nobody was checking. For a crop of a Windows window that means `Add-WindowFrame -Cut <sides>`, which redraws the whole frame from DWM's model (below), so none of the translucent band survives. For a translucent-bordered crop `winframe.py` cannot model, pass `hairline.py --opaque`: it takes the ring's alpha to 255 where the ring is solid — which includes the shape's outer fringe, so a rounded corner comes out stepped rather than soft — and thresholds the silhouette *before* the supersample, since interpolating first drags samples across a threshold sitting inside that alpha plateau and leaves a staircase of half-strength pixels through the corner. **The flag is the project's to pass, not the script's to infer** — whether a frame is a crop of such a window is a fact about how it was taken. Two attempts that look right and are not: stroking only the cut sides (correct on white, two visible edges and two invisible ones on dark), and stroking all four while preserving alpha (colour diluted to whatever the native alpha allows, so the corner reads darker than the flats). Default it off — on a capture whose alpha is genuine coverage the same step squares the corners off. **For a Windows capture, draw the frame with `scripts/winframe.py` instead of editing the one Windows drew.** A captured Windows border is the border mixed with the shadow and backdrop behind it — its top-to-bottom shading is the drop shadow, not the border — so no treatment of those pixels recovers it. `winframe.py` keeps only the content inside DWM's clip and draws the frame from DWM's measured model (8 DIP corners, or 4 for a menu, flattened into chords; a 1 px antialiasing ramp; a uniform `rgba(117,117,117,0.40)` border for a window and an opaque `#E5E5E5` ring for a light menu, either of which `--ring` can replace). Drawn with Windows' own ring and the window's own shadow (`--shadow <style>`) it reproduces a real capture to under one level RMS. A capture script calls it through `Add-WindowFrame` in `windows-capture.ps1` rather than directly: that wrapper keeps the raw first and passes the ring every frame shares — `#BDBDBD` opaque, the colour `hairline.py` strokes and macOS draws round a decorated window, since Windows' own fades to 55 on a dark page — and no shadow, so a rounded Windows frame and a square hairlined crop read as one set.
       - **Take the colour from the set, not from a principle.** Matching what the platform strokes its own decorated windows with — `#BDBDBD` on macOS, measured — is what lets a bordered undecorated window sit beside a decorated one without looking edited, and that consistency matters more than contrast in the abstract. A mid grey on the reasoning that a light hairline vanishes on a light page reads as a drawn-on line among frames that all begin `(189, 189, 189)`. A set with nothing native to match takes `#BDBDBD` as well — a web app's region crops, or a Windows project whose own border `Add-WindowFrame` redraws — which is the ring these tools draw on every new frame. Frames an older capture bordered in another colour keep it until they are re-framed; nothing here recolours a set.
       - **Assert the border landed, and keep the raw.** A version of this drew the corners only — Pillow's rank filters replicate at the canvas boundary, so a straight edge running to the image edge erodes to itself — and reported success, because the check compared alpha before and after, which a border that was never drawn passes perfectly. Check for the colour on all four edges and refuse to write the file otherwise. **Assert the SKIP as well as the stroke**, which is the same hole one level up and was found by review rather than by use: the "this frame already has its own edge" path exits 0, indistinguishable from success to the capture script that called it, so a false positive from that gate ships an unbordered frame with nothing reporting it — and on a crop whose content runs to the edge, glyphs dense enough along a side can still read to that gate as a border. Pass `--require` from any caller that actually wants a border (the macOS capture lib does, unconditionally; the Windows one draws its frame with `winframe.py` instead). It asserts the *outcome* — all four edges carry the colour — rather than that a stroke happened, so re-running on an already-bordered frame stays idempotent while a frame carrying somebody else's border is refused. Separately: **keep the capture as it stands just before the frame step** — after any crop, `outline.py` included — as `raw/<name>` in the manifest's directory, `docs/screenshots/raw/`, committed with the frame. Every treatment here edits in place, so without a raw the only way to try a different one is to take the shot again — which needs the window on screen and the app in a staged state, neither of which survives the day, and on the other machine not at all. Tuning a border is post-processing and should not need the app running, so the raw travels with the repo rather than staying in one machine's `tmp/`.
     - **Read back what you captured** before wiring it in, and run it through the `screenshot-relevance` staleness check (*Examine every shot that has never been examined*) as if it were an inherited file: every literal in the frame must exist in source. A shot taken from a dirty working tree can already be wrong on the day it is committed.
     - Wire it in per the path table the `github-pages` skill owns, write alt text that says what the image shows rather than repeating the caption, and report the new file as part of the change set so it is committed with the prose it illustrates.

5. **Frame it.** Every frame this skill files carries an edge, chosen by what the frame is.
   - **Which framing tool follows from what the frame is, not from the platform alone:**
     - a Windows window, whole or cropped — `Add-WindowFrame` in `windows-capture.ps1`, which draws DWM's frame with `winframe.py`; `-Cut <sides>` names a crop's cut sides, which get the border straight along them, in a new margin outside the crop, with square corners, and `-Grow` covers a capture taken just inside the window's border, which shows as faint arcs at its corners; an opaque crop with no arc at any corner is a region crop and goes to the next item instead. `Add-WindowFrame` runs only from a script file inside the repo, since it finds the repo from its caller, and it commits nothing itself but writes the raw to `docs/screenshots/raw/<leaf of -Path>`. For an inherited or user-supplied Windows frame with no capture script, copy it to `raw/<name>` and run `scripts/winframe.py --kind window --shadow none --ring BDBDBD:1.0 --dpi <display DPI> [--cut <sides>] [--grow] raw/<name> --out <name>` directly. Pass the DPI of the display the shot came from: without `--dpi` the scale comes from the PNG's own `pHYs`, which a screenshot tool may write as 96 whatever the display's scaling, and the frame then gets the 96-DPI border and corners;
     - any other frame whose capture carries no edge, such as a region crop of a page or an undecorated macOS window — `scripts/hairline.py --require`, called from the capture script so a re-shoot is bordered by the same step;
     - a rounded subject captured whole, cropped to its own outline — `scripts/hairline.py --require --radius N` at that outline's radius, where the clip is the known-shape mask, so the corners are the subject's own arcs, and the ring goes outside them. A subject with its own border keeps it, and the ring goes outside that; a capture that arrives already keyed, with transparent corners from the two-backdrop solve, takes plain `scripts/hairline.py --require`, which traces the ring from its alpha. Measure the outline off the pixels rather than assuming it: an IntelliJ island's one-pixel border sits half a pixel outside the component's inset bounds, and its radius, fitted to that border, is the theme's `Island.arc` halved;
     - a rounded subject whose only capture was cropped inside its corners and cannot be taken again — `scripts/hairline.py --require --radius N`, with `--cut <sides>` for the crop's cut sides; N is the subject's own radius, which for an IntelliJ Islands panel is half the theme's `Island.arc`, 15 px at 144 dpi. A capture you can still take goes to the item above instead.

     Copy the file as it stands just before the stroke — after any crop, `outline.py` included — to `raw/<name>` beside the manifest, where it is committed with the frame, and keep that directory out of the published site — for Jekyll, an `exclude:` entry in `docs/_config.yml` — since a raw is an input to the frame step, not documentation. A re-capture overwrites its raw, and git keeps the one before. Show before and after on the contact sheet with the theme toggle on dark, which is the view that proves the edge is there.

6. **File it.**
   - **Filing any replacement, whoever produced it.** A user-supplied replacement — with nothing attached, the newest PNG on their Desktop — is filed the same way as a captured one. Compare its dimensions against the file it replaces with `file <path>` and raise a mismatch before going further, bordered with bordered: allow for the framing step the committed frame went through — `hairline.py`'s outward border adds 2 × the ring width, `winframe.py` adds the border thickness for each `--cut` side, or on every side under `--grow` — and compare with the outgoing file — its `tmp/screenshot-originals-<date>/` copy, or `git show HEAD:<path>` once a capture script has already written the path. A raw compares only with a raw, and the outgoing one is `git show HEAD:<dir>/raw/<name>`: the one in the working tree is already the replacement's, since the capture that re-shoots a frame overwrites the raw of the same name. Then copy it into place and run the `screenshot-relevance` neighbourhood sweep (*When a shot is stale, sweep its neighbourhood*) so the caption, alt text and prose move with it. Do not overwrite the committed image until the replacement is in hand and accepted.
   - **Write every artifact this run produces into the repo's own gitignored `tmp/`, never `$TEMP`.** The file tools refuse reads outside the working directories, so a sheet written to `$TEMP` is one this skill can build and hand over but never open again to check — which breaks the rule that sends it to a browser in the first place. A project-local `tmp/` needs no read grant, behaves identically on the Windows and macOS machines, and cannot collide with another repo's run. The global excludes file ignores `/tmp/` at every repo's root, so the project's `.gitignore` needs no entry of its own — and the `gitignore-scope-global` rule refuses one as a duplicate; `git check-ignore -q tmp/x` confirms it before the first write. Keep a descriptive `<artifact>-<date>` name for the sheet and for the directory of saved originals — the repo name that used to be in it is now carried by the directory. Apply the same rule to anything else this skill writes outside the change set.
   - **Every replacement is reversible.** Copy the outgoing file to `tmp/screenshot-originals-<date>/` *before* overwriting it — `auto` replaces without asking, which makes the undo path the only thing standing between an unattended run and a lost image. Do **not** delete those copies when the user accepts: for a frame git never had they are the only previous version — the one `contact-sheet.py` reads when it rebuilds the sheet, and the one **revert** copies back. A sheet already built embeds every image and renders either way. For a tracked image the copy is belt-and-braces anyway — `git checkout -- <path>` restores the committed version, and `git show HEAD:<path>` recovers it for the sheet — so the copy exists for the untracked case, for as long as the sheet may need rebuilding or the change reverting.
   - **Record the examination.** Set the entry's `verifiedAt` to `at-capture`: the frame was examined by being re-taken, and its sha is not known until the commit that carries it.

7. **Show it, then ask.**
   - **The contact sheet is how pictures are put in front of the user, and it comes before the change more often than after.** Any run with something visual to settle writes one HTML page into the repo's gitignored `tmp/` and links it — a stale frame, a proposed replacement, a verdict worth a second pair of eyes. Under `confirm`, `never`, and an absent policy the sheet **is** the proposal, so it is written *before* any capture: "say what changed and what the replacement would show" is a claim about pictures, and no amount of prose puts the picture in front of the person deciding. Only `auto` writes it afterwards, as evidence of a swap already made — permission to skip the question is not permission to skip the evidence, and an image swapped unattended is exactly the one whose before and after must be easy to compare. **The trigger is a picture changing on disk, not a reply mentioning one and not a run ending.** Any turn that writes an image file ends with a sheet, unasked — whatever produced it, whichever skill is loaded, and however small the change. The earlier wording keyed on whether the reply "says anything about" an image, and that is a hole a reply can walk through by saying little; the file changed either way, and the user cannot see it. **Iteration counts as changes, not as one change:** re-shooting the same frame five times while tuning it is five sheets, because each one moves the point of comparison, and the run that ends with "it looks right now" is precisely the one whose claim nobody has been shown. If that feels like a lot of sheets, the answer is fewer speculative re-shoots, not fewer reports. Skip it only when the turn touched no image at all. The rationalisations for skipping are always the same and always wrong: *the change is one pixel* (an argument for magnified crops, not against the sheet), *it is uniform across many images* (uniformity is itself a claim about images), *they have seen a representative example inline* (a sample the reader did not choose, so they cannot see the one that went wrong), and *this was not a documentation run* (the pictures do not know that). Every time this was skipped the thing missed was visual and uncatchable in prose. A fifth rationalisation is newer and is the one to watch for: *the user is watching me work and will say if it looks wrong*. They said it four times in one session — a border 41% too thick on curves, a border doubled to 4px on the sides that already had one, a frame left on a superseded border, and a corner that read thin — each after a reply that had described the change in prose and shown nothing. Being asked for the report is the failure, not the reminder. Build the sheet **before** writing the summary, and let the summary point at it rather than repeat it.
   - **What goes on it.** Every screenshot, not only the ones in question — anything replaced as a before/after pair with both sets of dimensions, everything else as the picture currently committed. **Every file the frame step touched also carries its unframed stage**, the capture as it was before `hairline.py` or `winframe.py` ran: always in the page, and hidden until the reader ticks the nav's **Show before framing** checkbox, which starts unticked on every load. The committed version a replacement supersedes sits behind a second nav checkbox, **Show previous version**, which starts ticked. "Unchanged" and "not implicated" are claims about an image, so a page that argues them in prose while showing only the ones that changed asks the reader to take the quiet ones on trust; it is also where a wrong verdict gets caught, since this check reads text and cannot see layout, a cropped edge or a control that moved. Each frame carries its staleness proof, and each one awaiting a decision carries what a re-capture would need — the session, the app state, the preconditions — so the cost of the shot sits beside the case for it. **Build it with `scripts/contact-sheet.py`** — `python ~/.claude/skills/screenshot/scripts/contact-sheet.py --notes <notes.json>`, run from anywhere in the repo. It derives the page from the manifest, the images, `raw/<name>`, git at `--base` and the saved originals, copies the fixed parts from `references/contact-sheet.html`, writes `tmp/screenshot-contact-sheet-<date>.html`, publishes it on the tailnet through `~/.claude/skills/shared/tailnet_publish.py` and prints the URL, or the page's `file:///` URL after a `NOTE:` giving the reason when publishing fails. The one hand-written part is the notes file — the verdicts in words, each frame's proof and what a re-capture would need, the lede and the G-series gaps — whose schema is in the script's docstring; keep it in the repo's `tmp/` beside the sheet. The dots and verdicts compare against `--base`, `HEAD` by default, and the legend calls that "this session": once the session has committed, pass `--base <first-session-commit>^` on every later build, the commit `HEAD` was at before the session's first commit, read from `git log`. The builder needs a `screenshots.json`; for pictures outside a manifest — an icon, a candidate in `tmp/`, a screenshot the user supplied — build the page from the template's parts by hand, keeping its data URIs, theme toggle and corner crops. Otherwise do not fill the template's slots by hand or hand-roll the HTML from this description: the script is what makes two runs, in two repos, by two agents, produce the same page, and a sheet built another way silently drops the parts described nowhere else: the `#intro` section with its lede and the summary table of every frame, the legend, `W × H → W × H` in each meta line, the 6× nearest-neighbour corner crops that carry pixel-level proof, the `#theme` toggle that tests a contrast claim against both themes, the **Show previous version** and **Show before framing** checkboxes, and ← / → stepping. `references/screenshot-manifest.md` explains why each part is there. Open the finished page in a browser before handing it over, which is the check that catches what grepping the HTML cannot. Do **not** substitute reading images into the transcript: they arrive in the order they were read, split by tool output, and six pictures from a three-image run cannot be paired up by eye.
     **Hand over the URL the script printed, verbatim, as a Markdown link** and let the user open it themselves: the tailnet URL opens on either machine, where a `file:///` link opens only on the one that wrote it. When the script fell back to `file:///`, hand that over with the reason from its `NOTE:` line, never as a silent substitute. Do not open it through an annotation tool: that returns nothing a reply cannot carry, and is not how these get read. Embed each image as a **base64 `data:` URI**, never a path, so the page is self-contained: the sheet and the saved originals sit in different directories, and a sheet that still renders after `tmp/` is cleared is worth the bytes. Scale for display with CSS (`max-width`) — never by touching the file. A clean pass stays a one-line text summary: do not open a browser to say nothing is wrong.
   - **Number the frames, and make them one click apart.** Every entry gets a number matching its manifest order, shown in its heading and used in the chat write-up too, so "re-shoot 2 and 6" is unambiguous where "the help one and the crew suits one" is not. The sheet carries a fixed list of those numbered entries down the left, outside the content column, each switching to its frame on a single click; a page that can only be scrolled makes the reader hunt for the shot they were just told about. Keep an **All frames** view alongside it for reading straight down, since the argument for showing every frame is that they get compared.
   - **Then ask, with the sheet open.** The page states the case; it does not collect the decision. Ask once, covering every screenshot in question, and let the user settle each on its own — a run that proposed three replacements may have got two right. **Before a capture** the question is which frames to shoot, and whether the framing described is the one they want. **After one** it is keep, revert, or re-capture: **revert** copies the saved original back; **re-capture** means the framing was wrong, so change `docs/screenshots/capture/<id>.sh` and run it again — never re-shoot by hand around a script that produced the wrong thing, because the next run would reproduce that same wrong thing.
   - Do not restate layout or markup rules here — `~/.claude/skills/github-pages/SKILL.md` owns the `docs/screenshots/` location, the per-page relative-path table, and the hero-versus-inline image markup. Consult it when a screenshot has to be added, moved, or re-pathed.

## Out of scope

- Do NOT capture a frame whose entry says `never`, or one with no `policy`, unless the user asked for it or approved it — a run that only found it stale reports it and stops
- Do NOT write a `policy` the user did not give you, and do NOT raise one (`never` → `confirm` → `auto`) on their behalf
- Do NOT add a screenshot flag, demo mode, or seed-data hook to the product to make a capture easier. This holds even with a capture approved: permission to take the picture is not permission to change the product so the picture looks better. A fixture replayed through an input the product already takes is not such a hook. If neither real use nor such a fixture can reach the state, the shot is the user's to take
- Do NOT delete an image file, and do NOT remove a manifest entry, without explicit confirmation
- Do NOT copy a helper from `scripts/` into a project; the project calls it by its path under `~/.claude/skills/screenshot/scripts/`
